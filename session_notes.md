What's built (7 phases, all implemented and smoke-tested)

Cart — guest carts via X-Cart-Token header, /cart/merge on login, full item CRUD.
Pricing service (app/services/pricing.py) — quantity-tier pricing (PRD section 22) and promo codes. Fixed a real bug: quantity tiers were overriding negotiated wholesale/distributor prices even when worse for the customer — now takes min() so tiers only ever discount, never surcharge.
Cart wired to real pricing — live discount/total preview, promo validation.
Checkout → Orders — Order/OrderItem/OrderStatusHistory models (price/name snapshotted per PRD section 53), order_service.py (transactional checkout, reservation on the PAID transition per PRD section 19, release on cancel), pluggable PaymentGatewayBase/StubPaymentGateway and NotificationBase/LoggingNotifier (no real providers chosen — intentionally stubbed, not faked).
Admin order + inventory management — /admin/orders/*, /admin/inventory/{sku_id}, RBAC-gated via require_role(...).
Admin promo code CRUD — /admin/promo-codes/* (create/list/get/update; no hard delete — deactivate via is_active instead, to protect the FK from historical orders).
Also earlier, before phased work began: catalog read side — Category/Product/ProductVariant/SKU/Inventory models, /categories/, /products/, /products/{slug}.

Payment gateways and merchant webhooks (2026-08-15)
  - Payme uses its merchant JSON-RPC protocol at `/payments/payme/webhook`: Basic authentication, CheckPerformTransaction, CreateTransaction, PerformTransaction, CancelTransaction, CheckTransaction, and GetStatement. Provider transactions are persisted and idempotent.
  - Click uses its Prepare/Complete callback protocol at `/payments/click/webhook`: action-specific MD5 signature, service ID, amount, and prepare ID are validated before payment is recorded. Callback retries are idempotent.
  - `app/services/payment/registry.py` is the shared registry for Payme, Click, Stripe, and PayPal. Checkout and payment confirmation resolve gateways through it; the webhook router is registered in `app/main.py`.
  - Uzum Pay is explicitly blocked pending merchant-supplied API documentation, signing rules, and sandbox credentials. It is not exposed as a checkout method and no guessed integration has been added.
  - `app/schema_mariadb.sql` now contains current order fields plus `click_transactions` and `payme_transactions`. Use the complete schema for a fresh database; existing MariaDB databases need equivalent migrations.
  - Local checks cover imports, compiled MariaDB DDL, and protocol handlers. A full payment cycle still requires each provider's sandbox credentials and a public HTTPS callback URL.

Frontend-readiness fixes (2026-08-15)
  - CORS is configured through `CORS_ORIGINS` (comma-separated; local Vite defaults included) and exposes `X-Cart-Token` so browser clients can retain guest carts. Production must set `CORS_ORIGINS` to the deployed frontend origin.
  - `GET /payments/methods` lets the frontend show only configured payment options and reports Uzum Pay as blocked pending merchant API documentation. It never exposes secrets.
  - `POST /orders/` returns a checkout-only `payment` object with the provider reference (redirect URL, Stripe client secret, or PayPal order ID). It also returns a one-time guest-order token for guest orders. Normal order endpoints never return either secret.
  - Guest `GET /orders/{id}`, `POST /orders/{id}/confirm-payment`, and `POST /orders/{id}/cancel` require `X-Order-Token`; account orders require the owning JWT. Checkout now validates payment configuration and keeps order/cart/promo changes in one transaction, so unavailable providers and provider request failures roll back cleanly.
