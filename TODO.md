## What's already done (this session, backend only, SQLite-tested — not yet run against real MariaDB)
- Automated test suite committed: `tests/` (pytest, 58 tests, `requirements-dev.txt` adds `pytest`/`fakeredis` — dev-only, not in `requirements.txt`). Run with `pip install -r requirements-dev.txt && pytest tests/ -v`. `tests/conftest.py` spins up a fresh in-memory SQLite database per test (with the `BigInteger`→`INTEGER` compiler patch this whole session's verification relied on — see its docstring) and provides `client`/`db_session`/`sku`/`warehouse` fixtures plus `register`/`login`/`make_admin` helpers. Covers everything built this session: reservation/TTL/state-machine (`test_orders_reservation.py`), multi-warehouse selection (`test_warehouses.py`), Payme/Click webhooks + refunds (`test_payments.py`), quote conversion (`test_quotes.py`), auth/email-verification/MFA (`test_auth.py`), tax engine (`test_tax_engine.py`), notification templates (`test_notification_templates.py`), integration retry/DLQ (`test_integration_log.py`), analytics capture (`test_analytics.py`), rate limiting incl. the Redis path via `fakeredis` (`test_rate_limit.py`), and warehouse/inventory admin CRUD (`test_admin_warehouses.py`). Does **not** cover pre-existing features from before this session (catalog CRUD, promo codes, addresses, wishlist beyond analytics, reviews) — those still have no committed tests.
- Analytics event capture (PRD §46/§49): `AnalyticsEvent` model (event_name/user_id/session_id/properties JSON) + `app/services/analytics.py:record_event()` (never raises, same isolation principle as notifications/CRM — an analytics write failing must not fail the request it's describing). Wired at: `sign_up`/`login` (`auth.py`), `add_to_cart` (`cart.py`), `begin_checkout` (`orders.py` checkout), `purchase` (single choke point: `order_service.set_order_status()`'s PAID transition, so it fires exactly once regardless of which gateway/path completed payment), `generate_lead` (`quotes.py`), `add_to_wishlist` (`wishlist.py`). Admins can read them via `GET /admin/analytics-events/` (Marketing Manager). **This is capture only — nothing is forwarded to GA4/Meta/GTM yet**; that needs their Measurement Protocol credentials, which haven't been chosen (flagged above). `view_item`/`view_item_list`/`search`/`remove_from_cart`/`add_payment_info`/`refund` from PRD's full GA4 list aren't wired yet either — the ones above are the highest-value conversion events, not the complete list.
- `/api/v1` URL prefix (PRD §43): every router is now mounted under one versioned `APIRouter(prefix="/api/v1")` in `app/main.py` instead of at the app root. Updated `app/dependencies.py`'s `oauth2_scheme` tokenUrl, and the frontend's `frontend/src/api/client.js` `API_BASE_URL` default + `frontend/.env.example` to include `/api/v1` — the frontend's individual `api/*.js` call sites still use bare paths like `/cart/items`, so only the base URL needed to change. This was a good time to do it since PRD §13's own frontend/backend were never actually run against each other yet (per this file's Frontend section).
- Multiple warehouses (PRD ТЗ№3 §27/§28/§68): `Warehouse` model (name/country/priority/is_active) + `/admin/warehouses/*` CRUD (Warehouse Manager). `Inventory` now belongs to a specific warehouse (unique on `(sku_id, warehouse_id)`, not `sku_id` alone), so `/admin/inventory/{sku_id}` lists every warehouse's row for that SKU, `POST /admin/inventory/{sku_id}` adds stock at another warehouse, and `GET`/`PATCH /admin/inventory/{sku_id}/{warehouse_id}` target one row. `SKU.available_quantity` and `order_service.available_stock()` sum availability across every *active* warehouse. Creating a new SKU (`POST /admin/variants/{id}/skus`) now requires at least one active warehouse to exist — it 400s with a clear message telling the admin to create one first, rather than guessing a default.
  - **Reservation is single-warehouse-per-line, not split-fulfillment**: `_reserve_stock()` picks the highest-priority (lowest `Warehouse.priority`) active warehouse that *alone* has enough stock for that line, and records it on `OrderItem.warehouse_id`. PRD §68 explicitly allows "manual priority" as sufficient for phase 1 and does not require splitting one line across warehouses — so a line that no *single* warehouse can cover is rejected as insufficient stock even if the sum across warehouses would be enough. Flagging this precisely so it isn't mistaken for full multi-warehouse fulfillment.
- Admin MFA (PRD §58), TOTP-based via `pyotp` (new dependency, offline — no SMS/email OTP provider needed): `User.mfa_secret`/`mfa_enabled`, `POST /auth/mfa/setup` (returns secret + QR provisioning URI), `/auth/mfa/enable`, `/auth/mfa/disable` (both require a valid current code), all rate-limited. `POST /auth/login` accepts an optional `mfa_code` and enforces it once `mfa_enabled` is true for that account. **Not** force-enabled for admin roles globally — it's opt-in per account, because there's no verified flow here for handing a brand-new admin account a paired authenticator app, and flipping it to mandatory for every SALES_MANAGER/PRODUCT_MANAGER/etc. account today risks locking accounts out. See the flagged TODO item above.
- Integration retry/DLQ (PRD §52-57): `IntegrationLog` model (one append-only row per attempt, like `OrderStatusHistory`). `app/services/integrations/log.py:run_with_log()` wraps an integration call, never raises, and records SUCCESS/FAILED/DEAD_LETTER (after `max_attempts`, default 5). `Bitrix24Connector.push_order`/`push_quote` now return `bool` (previously `None`, swallowing failures silently) so the wrapper can tell success from failure. Wired into every CRM push call site (`orders.py` checkout/confirm-payment/cancel, `quotes.py`). `app/services/integrations/retry.py:retry_failed_integrations()` re-dispatches every integration whose *latest* attempt is FAILED (not DEAD_LETTER — those need a human) via a small dispatch table; scheduled externally through `app/tasks/retry_integrations.py` (same "no task queue yet, use cron" pattern as `expire_reservations.py`). Admins get `GET /admin/integration-logs/` and `POST /admin/integration-logs/{id}/retry` (Super Admin) for manual retry, including of DEAD_LETTER rows. Only CRM/Bitrix24 is wired into this so far — email notifications still fail silently (logged only, no IntegrationLog row); wiring `EmailNotifier` through the same wrapper is a small follow-up if email delivery failures need the same durability.
- Tax engine (PRD §41/§69): `TaxRule` model (country/customer_type/tax_type, "*" wildcards — same lookup shape as `ShippingRate`) + `/admin/tax-rules/*` CRUD (Accountant). `Order.tax_amount` is now computed at checkout on the post-discount subtotal (pipeline: subtotal → discount → **tax** → shipping → total, per PRD §69) and previewed in `GET /cart/?country=`. Unlike shipping, an unconfigured country/customer_type is *not* an error — it just means 0 tax, since PRD gives tax no "must be configured" acceptance criterion the way it does for shipping.
- Notification templates: `NotificationTemplate` model (event/locale/channel/subject/body/is_active, PRD §42) + `/admin/notification-templates/*` CRUD (Marketing Manager). `EmailNotifier` now checks for an active DB template before using its hardcoded copy (falls back: requested locale → `en` template row → hardcoded string), so it keeps working with zero rows configured. Only `email` channel is wired up (SMS/WhatsApp/Telegram templates can reuse the same table once those providers exist). Locale is currently always `"en"` when notifiers call it — there's no per-user/per-order locale preference yet, so ru/uz templates work but nothing selects them automatically.
- Rate limiting moved to Redis (`app/core/rate_limit.py`, needs the `redis` package now in `requirements.txt`): sliding window via a Redis sorted set (ZREMRANGEBYSCORE + ZCARD + ZADD/EXPIRE), shared correctly across worker processes. Set `REDIS_URL` in `.env` to activate it. Falls back to the old in-process deque limiter — logged once — if `REDIS_URL` is unset *or* Redis is configured but unreachable, so a Redis outage degrades rate limiting instead of taking the API down. Verified against `fakeredis` (dev-only, not added to `requirements.txt`) since no real Redis server is reachable from this dev machine.
- Email verification: `User.email_verified` (PRD §19), `EmailVerificationToken` model, `POST /auth/verify-email`, `POST /auth/resend-verification` (rate-limited, no-op if already verified). Registration now sends a verification email automatically. Nothing currently gates on `email_verified` being true (no PRD acceptance criterion requires blocking login/checkout on it) — it's informational/available for the frontend to show a "verify your email" banner.
- Quote → Order conversion: `POST /admin/quotes/{id}/convert` (Sales Manager). Requires the quote be `ACCEPTED` with a `proposed_price`/`currency` set first (existing `PATCH /admin/quotes/{id}`), snapshots that price into a new order, and stamps `QuoteRequest.order_id` to block converting the same quote twice. The RFQ form only collects free-text products/quantity (PRD §32), not per-SKU lines, so the order gets exactly one line item describing the whole quote — not fabricated SKU rows. Admin supplies the shipping address at conversion time since the RFQ form never collects one.
- Stock reservation moved to order creation (status NEW), not just PAID (PRD §19/§63) — closes the "two guests hold the last units" race. Reservation is atomic (row-locked `_reserve_stock`), has a TTL (`Order.reservation_expires_at`, `settings.RESERVATION_TTL_MINUTES`), and is released by `expire_stale_reservations()` — called opportunistically from every checkout and by the new standalone `app/tasks/expire_reservations.py`, which **needs to be scheduled externally (cron/systemd/Task Scheduler)** since this project has no task queue.
- `PAYMENT_FAILED` and `PARTIALLY_REFUNDED` added to `OrderStatus` (PRD §60/§23) and wired into `_ALLOWED_TRANSITIONS`. Payme/Click webhooks now move an order to `PAYMENT_FAILED` on expiry/decline/pre-payment cancel (releasing its reservation), and allow retrying payment on the *same* order afterward (re-reserving stock, correctly rejecting the retry if stock ran out meanwhile).
- Refunds: `Refund` model + `POST /admin/orders/{id}/refund` (Accountant/Sales Manager), supports partial refunds (accumulates to `PARTIALLY_REFUNDED`, closes out to `REFUNDED`), rejects over-refunding. `PaymentGatewayBase.refund()` implemented for Stripe (documented Refunds API) and PayPal (capture-lookup + refund) — both real but **unverified against a live/sandbox account**, same disclosure as the rest of that module. Payme/Click `refund()` deliberately raise `RefundNotSupportedError`: neither has a documented *outbound* merchant refund endpoint verified in this codebase (their protocols are inbound-webhook-only), so those must still be refunded manually from each provider's merchant cabinet. Reconciliation against provider records is still open — not built.
